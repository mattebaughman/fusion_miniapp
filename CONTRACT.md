## The simulation task
```python
# fusion_miniapp/sim.py  -- top-level, importable by name, picklable arguments and result
def evaluate(candidate: dict | None = None, knobs: dict | None = None, agent_id: str = "", seed: int = 0, *,
             params: dict | None = None, candidate_idx: int = 0, generation: int = 0,
             monitor: dict | None = None) -> dict: ...
```
- `params`: a full parameter dict from the parent's outer loop (`initialize_population` / `repopulate`, 15 keys with the strings `model` and `kind`), passed to the parent's worker unchanged as `(params, None, candidate_idx, kw)` with `kw["generation"] = generation`. Or `candidate`: any subset of the seven mutable profile parameters `a1_ne, gamma_ne, Delta, a2_ne, a1_Te, gamma_Te, a2_Te`, the rest filled deterministically from `seed` with the parent's own sampler (not both).
- `knobs`: the `sim` section of the knob file as a dict (None means the smoke preset).
- `monitor`: the `monitor` section (a partial dict is merged over the smoke preset's); None records no trace. With `capture`, the record gains `trace` (2026-11-23, entry 9 below).
- Returns a JSON-serialisable dict: the parent worker's scalar result record (NaN as None), plus `emulated: true`, `device`, `t_start` (epoch, when the worker started it), `elapsed_seconds`, `worker_peak_rss_mb`, `touches` (a dict of touch-kind to count) and `touch_check` (`"pass"` or `"fail: <which>"`); a cold start adds `cold_start: true`.
- It runs the parent's real `_evaluate_single_candidate` / `evaluate_final_innerloop` over stand-ins injected through the adapter's `context` (keys `core_edge_optimization`, `run_matey_inference`, `puff_optimizer`). The context is built once per process and set of context knobs, and cached. With `sim.cold_start_fraction` f, an evaluation whose hash of (agent_id, generation, candidate_idx) falls below f runs in a fresh single-use `python -m fusion_miniapp.sim` process started inside the task, tied to its worker by a pipe.
- A fixture twin `evaluate_fixture(...)` with the same signature returns the same keys instantly with `emulated: true, fixture: true` and no torch import, for large agent-count tests.

## Knob file (YAML; `knobs.py` loads, validates, applies presets `smoke`, `hundredk`, `ignos_shape`, then knob files in order)
```yaml
sim:      {nodes_per_plane, planes, rollout_steps, puffs, fixed_point_cap, model_width, checkpoint_mb, device, cold_start_fraction, keep_artifacts, work_root, threads_per_worker}
agents:   {count, first, per_process, max_live, cost_scale (number or list), thinking_budget, budget_scales_with_cost}
tools:    {constraints_lookup, abstract_lookup, latency_ms}
llm:      {mode: stub|openai|off, base_url_env, api_key_env, model, send_thinking_budget, timeout_s, max_retries, min_model_share, max_empty_share, stub_latency_s, max_in_flight, admission_tokens, thinking: null|off|on, reply_cap, temperature, top_p, outage_s}
workers:  {sim_workers, gpu_per_worker}
outer:    {population, generations, generator: llm|mutation, rng: shared|per_agent, logs: per_agent|none, wall_weight, noise, parent_stdout: keep|drop}
monitor:  {capture, fixture_trace: smooth|hash, weight}
campaign: {slots, mode: generations|async, warmup, notes}
record:   {extras}
```

## The decision logic (no agent-framework import in this file)
```python
# fusion_miniapp/decide.py
class Services(Protocol):
    async def llm(self, agent_id, messages, thinking_budget, reply_tokens) -> str: ...
    async def simulate(self, agent_id, params, candidate_idx, generation, seed) -> dict: ...   # one evaluate
    async def lookup(self, agent_id, what) -> dict: ...                                         # tool call
    async def remember(self, agent_id, state) -> None: ...                                      # memory / checkpoint
    async def report(self, agent_id, result) -> None: ...                                       # to the campaign manager
```
- A campaign is the parent's three roles, each with its own memory and step functions:
  - Generator: `generator_state`, `generator_step` (initialize / repopulate, plus the llm-mode refill call).
  - Evaluator: `evaluation_calls`, `evaluate_population`.
  - Coordinator: `coordinator_state`, `start`, `on_population`, `on_evaluated` (select_survivors, update_best_result and log_generation in one step), `summary_messages`, `finish`.
- `run_campaign(agent_id, seed, knobs, svc, generator, evaluator, ask, out=None, on_state=None)` is the Coordinator's whole run against two handles with `initialize(msg)`, `repopulate(msg)` and `evaluate(population, generation)` (the Academy layer). The LangGraph layer runs the same steps as subgraph nodes.
- The random generator's state travels as a JSON string in the repopulate message (`outer.rng: shared`), or each role keeps its own `SeedSequence(seed).spawn(2)` stream (`per_agent`).
- A campaign's result (one line of `agents.jsonl`): `{agent_id, seed, best, generations, summary, sources, refill, n_llm_calls, n_sims, n_tool_calls, budget, touches, devices, touch_checks, fixture, sim_s, wait_s, worker_peak_rss_mb, t_start, t_end, llm_call_details}`; on the AUTONMI layer with `record.extras`, also `monitor` (each candidate's Monitor numbers, outside `record.comparable`).
- With the stub LLM and a fixed seed, the result (`record.comparable`: without timings, memory, touch counts and device names) must be identical whichever agent layer runs it; with `generator: mutation`, the campaign's `evolution_log.csv`, `evolution_log.jsonl` (timestamps aside) and `best_result.json` must equal the parent driver's (`tests/test_parent_oracle.py`).

## The two layers and the flag
- `layer_langgraph.py`: `async def run_agents(n_agents, knobs, svc_factory, out, *, first=0, emit=None, store=None, replicas=None) -> list[dict]`. One campaign graph per process with three compiled subgraphs (Coordinator, Generator, Evaluator) and mailbox keys, hosted by FlowGentic's `AgentHost` (`max_live_agents` = `agents.max_live` or all); `evaluate` is a suspending task tool on the process's RHAPSODY session, P calls per generation in one step.
- `layer_academy.py`: the same signature (without `store`, `replicas`): a `CoordinatorAgent`, a `GeneratorAgent` and an `EvaluatorAgent` per campaign, hosted in-process (local exchange, no executor), launched when the campaign gets one of `agents.max_live` slots and shut down when it ends.
- `run.py` entry point: `python -m fusion_miniapp.run [--agents N] [--use-academy] [--preset NAME] [--knobs FILE ...] [--sim real|fixture] [--llm stub|openai] [--out DIR]`. `--use-academy` is read once; the chosen layer is imported lazily.
- While running, both layers print one line per interval to stderr: `agents working=<n> waiting=<n> model_requests=<n> done=<n>`.
- `layer_autonmi.py` (proposed 2026-11-22): a third layer with its own entry point, `python -m fusion_miniapp.layer_autonmi [--agents N] [--preset NAME] [--knobs FILE ...] [--sim real|fixture] [--llm stub|openai] [--out DIR] [--populations N] [--workers N] [--runtime local|dragon] [--endpoints-file F] [--api-key-file F]`, not a `run_agents` for `run.py`: AUTONMI owns the processes, the engines and the run's telemetry. Each campaign is three AUTONMI scripted agents, one per role, plus `campaign.slots` Monitor agents (since 2026-11-24, entry 1 of that date below; from 2026-11-23, entry 8, three agents; before, one agent per campaign); a generation's P candidates go on the campaign's candidate queue, and each Monitor runs the next one's `evaluate` as one suspending task tool. Populations default to `run.py`'s agent processes. It writes `run_record.json` and `agents.jsonl` with `record.write`, as `run.py` does (`agent_layer: autonmi`, with an `autonmi` section), and exits as `run.py` does (0, 1, 143); `compare_records` must find its results equal to the other layers' and to the recorded references (`tests/test_layer_autonmi.py`).

## The run record
`record.py` writes `<out>/run_record.json` (atomically): `status` (pass, fail, interrupted), `run` (time, host, Slurm job, this package's git commit and dirty flag, backend), all knobs, `agent_layer`, `emulated`/`method`/`note` (all physics output synthetic), package versions, the parent commit, the device probe, `counts`, `llm_service`, `llm_check`, `lookups`, the touch-check verdict summed over all evaluations, `speed`, `peak_rss_mb`, `threads`, pool statistics and `results_sha256`. `<out>/agents.jsonl` gets one line per finished campaign, streamed from this run's agent-process files, which are removed only after both files are in place. stdout ends with one `speed:` line. `compare_records.py` compares two records.

Messages use new per-agent inboxes (`Mailbox.deliver`, `take_all`, waiting or not) and the Generator waits for an empty queue (`Mailbox.emptied`); `Mailbox.most` keeps each queue's most items; `Mailbox.fail` counts a failed campaign's leftover items as dropped and clears them, so a `take_all` woken just before the failure does not also receive them. `monitor.Rolling` also holds the window (`recent`, `ends`) and `take_one`. `verify()` in this mode checks bounds (`messages()`) tied to each agent's cycles, and four new checks: `each_candidate_evaluated_once`, `survivors_within_the_population`, `inner_loops_within_the_slots`, `candidates_waiting_within_take`. Record, this mode only: `campaign_mode: async` and `counts.asynchronous` (results scored and kept, in all and after warm-up, of the campaigns that reported; cycles per role and the Generators' waits for survivors, from AUTONMI's rows, null when there are none, as after SIGTERM); a campaign's line has no `generations` entries (`counts.generations` is 0) and gains `t_submit` (each evaluation's submission time, beside `sim_s` and `wait_s`, which `record.write` reads for the evaluations' timings; a machine key, outside `results_sha256`), `n_cycles` and `survival` (its results scored and kept), and `memory_writes` counts Coordinator cycles; with `record.extras` each line also has `asynchronous` (each result's arrival, candidate, q, m, score, draw and kept; the Evaluator's and Coordinator's batches; the survivors message held at each profile; the final survivors), which `record.comparable` leaves out. `compare_records` compares two asynchronous records on their status (which holds the invariants), knobs, exact counts other than `feasible_agents` and `memory_writes`, and results scored, not on their digests. `config.json` of an asynchronous campaign says `rng: per_agent`, `generator: mutation` and `campaign_mode: async`.
3. **Each agent's model call, with tries and fallbacks (package 3).** New knobs: `llm.mode: off` (no model calls; `knobs.validate` refuses it outside the asynchronous mode), `llm.thinking` (null, off or on), `llm.reply_cap`, `llm.temperature`, `llm.top_p` (above 0, at most 1): each null by default, so every request is as before, and refused by `run.py`'s layers when set, as `campaign.notes` is; `llm.outage_s` (1,800, AUTONMI's, passed to `wait_for_servers`), and `campaign.notes` (false). On the AUTONMI layer `Script._ask` makes every call: by default the request is as before (`max_tokens` = thinking budget + the call's allowance, `thinking_token_budget`, `temperature: null`); `llm.reply_cap` sets `max_tokens` (plus the budget unless thinking is off); `llm.thinking: off` makes AUTONMI's transports send `chat_template_kwargs {enable_thinking: false}` and sends no budget, so no per-call `extra_body` replaces the transports' own; `temperature` and `top_p` are sent when set; the Generator's JSON schema (`decide.candidates_schema`) goes as a plain `response_format` keyword. A model run in the asynchronous mode needs `llm.thinking` set. In the asynchronous mode, unless `llm.mode` is off, each role makes its own call: the Generator one per take of 2 (prompt: the 2 profiles, the newest survivors, the Evaluator's latest scores, the Coordinator's guidance; last line "Candidates <a> and <b> of <B>: reply with a JSON list of 2 objects ..."; a value in the reply replaces the profile's, clipped to range, a key left out keeps the evolutionary loop's: `decide.parse_reconcile`, `async_reconcile`), each Monitor one per candidate (its note, `decide.note_messages`), the Evaluator one per cycle (each result's keep-probability, which is the score: `decide.scores_messages`, `parse_scores`, `async_model_scores`), the Coordinator one per cycle after it has sent the survivors (guidance, a new `guidance` message to the Generator: `decide.guidance_messages`); no summary call. A role's call that fails (an error, a reply its parse function cannot use, or a prompt whose characters plus `max_tokens` exceed the servers' smallest `max_model_len`, which is not tried again; the refill and summary are not checked) is tried up to `layer_autonmi.TRIES` (3) times, none once another agent has failed the campaign; then the role's fallback is used and counted: the profiles unchanged, no note, the score from numbers, no guidance, which is the `llm.mode: off` path. The Evaluator's prompt gives each result's q and m in full, and neither the score from numbers nor its formula. The stub LLM and `tests/fake_vllm.py` answer the three new calls by their last line (`llm.numbers_only`): the score from numbers, from that q and m at `monitor.weight`, and an empty note and guidance (the fake server a short text). In the generations mode the refill and summary calls are unchanged (one try; a failure fails the campaign, as in the other layers; changed by entry 4: 3 tries, then a fallback); `campaign.notes` adds a Monitor call per candidate and an Evaluator call per generation (an assessment, made before the results go on), which change no result. Record: each agent row and `counts.by_role` gain `model_asks`, `model_tries`, `model_fallbacks` (`model_calls` stays AUTONMI's count of replies); the asynchronous Generator's row gains `parameters_filled` (its proposals by parameters filled, 0 to 7), summed in `counts.asynchronous.parameters_filled`; an asynchronous candidate the reply filled has source `model` and counts in `refill_slots` (asked: every candidate the Generator's call was asked for); an asynchronous line's `n_llm_calls` is its agents' calls answered. The generations mode's refill and summary tries stay in `llm_call_details` as before; the roles' own calls' tries are there only with `record.extras`, else each population sums them (`layer_autonmi.CallSums`, written beside its lines as `calls-p<index>.npz` and removed once the record is written) into the record's `llm_service` and client-side counts (`record.write` takes a part's `call_times`). With `record.extras` only: each candidate's `note` (and in the generations mode `assessed`) in `monitor`, each Coordinator cycle's `guidance` in `asynchronous`, and those tries' details. `verify()` checks each agent's calls: asked one per cycle (a Monitor's per candidate; with `campaign.notes` a note per candidate and an assessment per generation), each answered or fallen back after at most 3 tries (`calls_as_planned`); messages: the Coordinator sends 2 per cycle with its call. `Mailbox.receive`: a message that has woken its receiver before its campaign fails is received, not also counted dropped. `compare_records` treats `llm.outage_s` as the model service's and leaves `llm_calls` out between two asynchronous records, and also `candidates_by_source` and `refill_slots` when they ran with `llm.mode: openai`. The asynchronous `config.json` says `generator: llm` when the roles make their calls.
4. **Record changes and inner-loop GPU placement (package 4).** The generations mode's refill and summary calls on the AUTONMI layer are tried up to `layer_autonmi.TRIES` (3) times while they fail (an error; a reply is used as before), then fall back, counted in `model_fallbacks` with the asks and tries: the refill keeps the parent's mutants (its slots stay `mutation` or `restart`, `refill.filled` 0), and the summary is left out (`summary: ""`); the campaign goes on (Matt's round-4 answer 12).
