## The inner-loop task
```python
# fusion_miniapp/sim.py  -- top-level, importable by name, picklable arguments and result
def evaluate(candidate: dict | None = None, knobs: dict | None = None, agent_id: str = "", seed: int = 0, *,
             params: dict | None = None, candidate_idx: int = 0, generation: int = 0,
             monitor: dict | None = None) -> dict: ...
```
- `params`: a full parameter dict from the parent's outer loop (`initialize_population` / `repopulate` / `mutate_params`, 15 keys with the strings `model` and `kind`), passed to the parent's worker unchanged as `(params, None, candidate_idx, kw)` with `kw["generation"] = generation`. Or `candidate`: any subset of the seven mutable profile parameters `a1_ne, gamma_ne, Delta, a2_ne, a1_Te, gamma_Te, a2_Te`, the rest filled deterministically from `seed` with the parent's own sampler (not both).
- `knobs`: the `sim` section of the knob file as a dict (None means the smoke preset).
- `monitor`: the `monitor` section (a partial dict is merged over the smoke preset's); None records no trace. With `capture`, the record gains `trace` (`trace.py`: `{"kind", "synthetic", "complete", "sections", "f32"}`; added instrumentation, not in IGNOS).
- Returns a JSON-serialisable dict: the parent worker's scalar result record (NaN as None), plus `emulated: true`, `device`, `t_start` (epoch, when the worker started it), `elapsed_seconds`, `worker_peak_rss_mb`, `touches` (a dict of touch-kind to count) and `touch_check` (`"pass"` or `"fail: <which>"`); a cold start adds `cold_start: true`.
- It runs the parent's real `_evaluate_single_candidate` / `evaluate_final_innerloop` over stand-ins injected through the adapter's `context` (keys `core_edge_optimization`, `run_matey_inference`, `puff_optimizer`). The context is built once per process and set of context knobs, and cached. With `sim.cold_start_fraction` f, an evaluation whose hash of (agent_id, generation, candidate_idx) falls below f runs in a fresh single-use `python -m fusion_miniapp.sim` process started inside the task, tied to its worker by a pipe.
- A fixture twin `evaluate_fixture(...)` with the same signature returns the same keys instantly with `emulated: true, fixture: true` and no torch import, for large agent-count tests.

## Knob file (YAML; `knobs.py` loads, validates, applies presets `smoke`, `hundredk`, `ignos_shape`, then knob files in order)
```yaml
sim:      {nodes_per_plane, planes, rollout_steps, puffs, fixed_point_cap, model_width, checkpoint_mb, device, cold_start_fraction, keep_artifacts, work_root, threads_per_worker}
agents:   {count, first, per_process, max_live, start_together, cost_scale (number or list), thinking_budget, budget_scales_with_cost}
tools:    {constraints_lookup, abstract_lookup, latency_ms}
llm:      {mode: stub|openai|off, base_url_env, api_key_env, model, send_thinking_budget, timeout_s, max_retries, min_model_share, max_empty_share, stub_latency_s, max_in_flight, admission_tokens, thinking: null|off|on, reply_cap, temperature, top_p, outage_s}
workers:  {sim_workers, gpu_per_worker}
outer:    {population, generations, generator: llm|mutation, rng: shared|per_agent, logs: per_agent|none, wall_weight, noise, parent_stdout: keep|drop}
monitor:  {capture, fixture_trace: smooth|hash, weight}
campaign: {slots, mode: generations|async, warmup, notes}

```
- Every knob added since the first release has a default that leaves the generations mode's earlier results and request bodies unchanged. The asynchronous mode's do not: a knob file written for it before entry 3 of 2026-11-24 now makes model calls (with the stub, every candidate comes from the stub's replies); `llm.mode: off` gives its old meaning, and with `llm.mode: openai` it needs `llm.thinking` set. `knobs.validate` refuses `outer.generator: mutation` in the asynchronous mode unless `llm.mode` is off (entry 2 of 2026-11-25). `run.py`'s layers refuse `campaign.mode: async`, `llm.mode: off` and the AUTONMI-only knobs set (`llm.thinking`, `reply_cap`, `temperature`, `top_p`, `campaign.notes`, `workers.gpu_per_worker`).
- `knobs/machines/stellar_ai_nemotron.yaml` is the StellarAI run path's (entry 5 of 2026-11-24).

## The decision logic (no agent-framework import in `decide.py` or `monitor.py`)
```python
# fusion_miniapp/decide.py
class Services(Protocol):
    async def llm(self, agent_id, messages, thinking_budget, reply_tokens) -> str: ...
    async def simulate(self, agent_id, params, candidate_idx, generation, seed) -> dict: ...   # one evaluate
    async def lookup(self, agent_id, what) -> dict: ...                                         # tool call
    async def remember(self, agent_id, state) -> None: ...                                      # memory / checkpoint
    async def report(self, agent_id, result) -> None: ...                                       # to the campaign manager
```
- A campaign is the parent's three roles, each with its own memory and step functions, and on the AUTONMI layer `campaign.slots` Monitors:
  - Generator: `generator_state`, `generator_step` (initialize / repopulate, plus the llm-mode refill call); in the asynchronous mode `async_generator_state`, `async_on_survivors`, `async_on_digests`, `async_on_guidance`, `async_waits`, `async_profiles` (the next `TAKE` = 2 profiles), `async_generator_messages`, `candidates_schema`, `parse_reconcile`, `async_reconcile`.
  - Evaluator: `evaluation_calls`, `evaluate_population` (the other layers); `keep_probabilities` (the parent's keep-probability, `q`); in the asynchronous mode `async_evaluate`, `async_score`, `numbers_score`, `scores_messages`, `parse_scores`, `async_model_scores`.
  - Monitor: `monitor.Rolling` (a campaign's rolling trace statistics: `hold`, `take`, `add`, `score`; the window of the last P scored results), `note_messages`, `parse_text`.
  - Coordinator: `coordinator_state`, `start`, `on_population`, `on_evaluated` (select_survivors, update_best_result and log_generation in one step), `summary_messages`, `finish`; in the asynchronous mode `async_coordinator_state`, `async_on_scored` (survival, the survivors, best-so-far, the log), `async_survivors`, `async_memory`, `async_finish`, `guidance_messages`.
- The asynchronous mode's prompts are bounded: a note or guidance shown inside a later prompt is cut to `NOTE_CHARS` (1,200) characters, and one Evaluator call shows at most `SHOWN_RESULTS` (8) results.
- `run_campaign(agent_id, seed, knobs, svc, generator, evaluator, ask, out=None, on_state=None)` is the Coordinator's whole run against two handles with `initialize(msg)`, `repopulate(msg)` and `evaluate(population, generation)` (the Academy layer). The LangGraph layer runs the same steps as subgraph nodes; the AUTONMI layer as hosted agents.
- The random generator's state travels as a JSON string in the repopulate message (`outer.rng: shared`), or each role keeps its own `SeedSequence(seed).spawn(2)` stream (`per_agent`; always in the asynchronous mode).
- A campaign's result (one line of `agents.jsonl`): `{agent_id, seed, best, generations, summary, sources, refill, n_llm_calls, n_sims, n_tool_calls, budget, touches, devices, touch_checks, fixture, sim_s, wait_s, worker_peak_rss_mb, t_start, t_end, llm_call_details}`; in the asynchronous mode also `t_submit`, `n_cycles` and `survival`; with `record.extras` also `monitor` and (asynchronous) `asynchronous`, outside `record.comparable`.
- With the stub LLM and a fixed seed, the result (`record.comparable`: without timings, memory, touch counts and device names) must be identical whichever agent layer runs it in the generations mode, at any `campaign.slots`; with `generator: mutation`, the campaign's `evolution_log.csv`, `evolution_log.jsonl` (timestamps aside) and `best_result.json` must equal the parent driver's (`tests/test_parent_oracle.py`). In the asynchronous mode one order of arrival, one seed and the Monitors' m give one campaign (`tests/async_replay.py`) with `llm.mode: off`, or with the stub when no model call fell back; which Generator takes fell back is a further input that the record does not hold, and a real model's replies are not recorded.

## The three layers
- `layer_langgraph.py`: `async def run_agents(n_agents, knobs, svc_factory, out, *, first=0, emit=None, store=None, replicas=None) -> list[dict]`. One campaign graph per process with three compiled subgraphs (Coordinator, Generator, Evaluator) and mailbox keys, hosted by FlowGentic's `AgentHost` (`max_live_agents` = `agents.max_live` or all); `evaluate` is a suspending task tool on the process's RHAPSODY session, P calls per generation in one step.
- `layer_academy.py`: the same signature (without `store`, `replicas`): a `CoordinatorAgent`, a `GeneratorAgent` and an `EvaluatorAgent` per campaign, hosted in-process (local exchange, no executor), launched when the campaign gets one of `agents.max_live` slots and shut down when it ends.
- `run.py` entry point for those two: `python -m fusion_miniapp.run [--agents N] [--use-academy] [--preset NAME] [--knobs FILE ...] [--sim real|fixture] [--llm stub|openai] [--out DIR]`. `--use-academy` is read once; the chosen layer is imported lazily. While running, both print one line per interval to stderr: `agents working=<n> waiting=<n> model_requests=<n> done=<n>`. They run the generations mode only and end a campaign at its first failed model call.
- `layer_autonmi.py`: the AUTONMI layer, with its own entry point, `python -m fusion_miniapp.layer_autonmi [--agents N] [--preset NAME] [--knobs FILE ...] [--sim real|fixture] [--llm stub|openai] [--out DIR] [--populations N] [--workers N] [--runtime local|dragon] [--slice I/K] [--endpoints-file F] [--api-key-file F] [--model-wait S] [--no-vllm-metrics] [--stagger-batch N] [--stagger-interval S]`. AUTONMI owns the processes, the engines and the run's telemetry. Each campaign is 3 + `campaign.slots` AUTONMI scripted agents (`a<i>/coordinator`, `a<i>/generator`, `a<i>/evaluator`, `a<i>/monitor<k>`) that talk only through `layer_autonmi.Mailbox` (exact keys, each campaign's candidate queue, each agent's inboxes), in `campaign.mode` generations or async. Each role's own model call is tried up to `TRIES` (3) times, then the role's fallback is used and counted; a call's request fields are `request_fields(knobs, budget, reply_tokens)`. It writes `run_record.json` and `agents.jsonl` with `record.write`, as `run.py` does (`agent_layer: autonmi`, with an `autonmi` section), and exits as `run.py` does (0, 1, 143); `compare_records` must find its generations-mode results equal to the other layers' and to the recorded references (`tests/test_layer_autonmi.py`).
- The StellarAI run path: `sbatch launch/stellar_ai_autonmi.sbatch [layer_autonmi arguments]`, configured by environment variables (`FUSION_MINIAPP_DIR`, `FUSION_ENV`, `FUSION_SCRATCH`, `RASCAL_REPO`, `FUSION_RUN_NAME`; `FUSION_MODEL_NODES` with `FUSION_MODEL_TIME` (and `FUSION_KEEP_SERVERS`), or `FUSION_MODEL_FLEET`; `FUSION_MPS`, `FUSION_MODEL_WAIT`, `FUSION_MEM_FLOOR_GIB`, `FUSION_DRY_RUN`, `FUSION_RUNTIME`, `FUSION_LAUNCHES`), exits with the run's status. Its fleet folder holds `endpoints` (the model jobs' own, combined in order), `api-key` (one key for every server, owner-only), `setup-files` (`layer_autonmi.SETUP_LIST`) and `model-<k>/`, each model job's folder. `python launch/probe_model.py [--logs DIR] [--timeout S] [--idle] <layer_autonmi arguments>` exits 0 when every server answers each role's request, 1 to stop the launch.

## The run record
`record.py` writes `<out>/run_record.json` (atomically): `status` (pass, fail, interrupted), `run` (time, host, Slurm job, this package's git commit and dirty flag, backend), all knobs, `agent_layer`, `emulated`/`method`/`note` (all physics output synthetic), package versions, the parent commit, the device probe, `counts`, `llm_service`, `llm_check`, `lookups`, the touch-check verdict summed over all evaluations, `speed`, `peak_rss_mb`, `threads`, pool statistics and `results_sha256`. `<out>/agents.jsonl` gets one line per finished campaign, streamed from this run's agent-process files, which are removed only after both files are in place. stdout ends with one `speed:` line. With `record.extras` (off by default) the record and the lines also hold the per-candidate and per-call detail; off, the toggle's additions are left out: the roles' own calls are counted, not listed (a line still holds its times, its best candidate, its summary and the generations mode's refill and summary call details). `compare_records.py` compares two records; `merge_records.py` makes one record of several launches' (entry 13 of 2026-11-26).
